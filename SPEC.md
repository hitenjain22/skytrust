## 1. The problem (why this exists)

I researched the major astronomy weather apps and sites (Astrospheric, Clear Outside, Clear Sky Chart, Meteoblue, 7Timer/Xasteria, Scope Nights, Good To Stargaze, and others) plus user reviews and forum threads. The consistent findings:

- **Forecasts disagree and nobody trusts one source.** Experienced astrophotographers routinely check 5–6 apps plus satellite loops before deciding to set up.
- **The #1 complaint is the "false clear":** the forecast says clear, the user spends an hour setting up, and it's cloudy. Users on forums report failure rates of roughly 20% to 40%+ on nights they set up based on a clear forecast.
- **High cirrus clouds** ruin deep-sky imaging but are often reported as "clear" by general weather forecasts.
- **No app tells you how often it has been wrong at your location.** Some show model agreement, but none I found show a verified track record.

## 2. The product (what we're building)

**One-line pitch:** *An astronomy cloud forecast that tells you how often it's been wrong.*

It works across three time horizons:

| Horizon | What it does |
|---|---|
| **Past — Track Record** | Backtest: for every night since January 2024 at several California sites, compare what each weather model predicted ~1–7 days ahead against what the sky actually did. Measure each model's accuracy, false-clear rate, and calibration. |
| **Present — Tonight** | Pull tonight's live forecasts from several models, combine them with a statistically trained blend, and output one calibrated number: "P(usable night) = 71%, best window 10pm–2am," plus how reliable that number has historically been at this site. |
| **Future — 7-Night Outlook** | Same thing for the next 7 nights, where the trust level honestly decreases with lead time because we *measured* how skill decays with lead time in the backtest. |

**Target user:** astrophotographers and observers in Northern/Central California.

**Measurable success criteria:**

- Backtest covers ≥ 5 sites, ≥ 3 weather models, January 2024 through the latest available data.
- Held-out test results reported honestly with confidence intervals, including whether the blend beats (a) the best single model and (b) climatology on Brier score. **If it doesn't beat them, that is still a valid result — report it plainly. Never tune on the test set.**
- App deployed publicly, loads from precomputed artifacts, and never crashes when an API is down.
- Offline test suite passes in CI.

## 4. Definitions (source of truth — do not change without asking)

All thresholds below live in `config/settings.yaml`, not hard-coded.

### 4.1 Time
- Store and compute everything in **UTC with timezone-aware timestamps**. Never use naive datetimes.
- Display in `America/Los_Angeles`.
- A **night** is keyed by the **local calendar date of the evening it begins**. "Night of 2026-01-10" = evening of Jan 10 through the morning of Jan 11 (local).

### 4.2 Dark window
- From **astronomical dusk** (sun altitude crosses −18° descending) to **astronomical dawn** (sun crosses −18° ascending) at the site's coordinates, computed with **Skyfield** (DE421 ephemeris).
- If a night has no astronomical darkness (not expected at California latitudes, but handle it), the dark window is empty; exclude the night and log it.

### 4.3 Dark hours
- The set of **top-of-hour UTC timestamps H** with `dusk ≤ H ≤ dawn`.
- Open-Meteo hourly cloud cover is an instantaneous value at H. **Verify this in Phase 0** and record it in DATA_NOTES.

### 4.4 Clear hour
- An hour is **clear** if cloud fraction ≤ `CLEAR_THRESHOLD` (default **0.20**, cloud fraction on a 0–1 scale).

### 4.5 Usable night
- A night is **usable** if its dark window contains a run of ≥ `MIN_RUN_HOURS` (default **3**) **consecutive** clear hours.
- Consecutive means timestamps exactly 1 hour apart. **A missing hour breaks a run.**
- Rationale: an imaging session needs continuous clear time, not scattered clear hours.

### 4.6 Observed labels (ground truth)

We use two independent-ish sources because each has a blind spot.

**(a) ASOS label — real observations, low/mid clouds only**
- Source: METAR reports from airport ASOS stations via the Iowa Environmental Mesonet (IEM).
- For each dark hour H, collect all observations with valid time in the window **(H − 30 min, H + 30 min]**.
- Map each reported sky layer (`skyc1`–`skyc4`) to a cloud fraction using okta midpoints:

  | Code | Oktas | Fraction |
  |---|---|---|
  | CLR / SKC | 0 | 0.0 |
  | FEW | 1–2 | 0.1875 |
  | SCT | 3–4 | 0.4375 |
  | BKN | 5–7 | 0.75 |
  | OVC | 8 | 1.0 |
  | VV (sky obscured) | — | 1.0 |
  | missing / M / blank | — | NaN |

  Make this mapping configurable. A "conservative" alternative maps FEW → 0.25, which makes FEW count as not clear; implement it as an option.
- METAR layer amounts are cumulative, so **hourly coverage = max over layers, then max over all observations in the window.** Taking the max is deliberately conservative: any cloudy report in the hour counts.
- No observations in the window → NaN for that hour.
- **Known blind spot:** ASOS ceilometers only detect clouds up to **12,000 ft above ground**. "CLR" means no clouds below 12,000 ft. **The ASOS label cannot see cirrus.** Document this everywhere results are shown.

**(b) ERA5 label — all cloud layers, but model-based**
- Source: ERA5 reanalysis via the Open-Meteo Historical Weather API (hourly `cloud_cover`, 0–100 → divide by 100). Also store `cloud_cover_low/mid/high` if available, for later analysis.
- **Known caveats:**
  - ERA5 is a reanalysis: a model constrained by observations, not a direct observation.
  - Its grid (~0.25°, roughly 28 km) is much coarser than a point.
  - **ERA5 is produced by ECMWF, so it may favor ECMWF forecasts** because they share model physics. Flag this in RESULTS whenever ECMWF looks best.
  - ERA5 has a publication lag of several days. Handle trailing missing days gracefully.

**(c) Primary label (used for training and headline results)**
- Per hour: `truth_cover = max(asos_cover, era5_cover)`. An hour is clear only if **both** sources agree it's clear. This lets ERA5 catch the cirrus that ASOS can't see.
- If one source is missing for an hour, use the other and set a flag. If more than 25% of a night's dark hours are missing in **either** source, exclude the night from the primary label and log the reason.
- `usable_primary` = the usable-night rule (4.5) applied to `truth_cover`.

**Always report metrics under all three labels** (primary, ASOS-only, ERA5-only) as a sensitivity analysis.

### 4.7 Forecast features (per site × night × model × lead)
- Source: Open-Meteo **Previous Runs API**, hourly `cloud_cover_previous_day{d}` for d = 1…7.
- **Lead d** = the value predicted about 24·d hours before its valid time. For a night's hours (e.g. 8pm–5am), the lead-1 values come from runs issued about 24h before each hour. That approximates "the forecast you'd check the day before." Document this approximation in LEARNING.md.
- **Why not the Historical Forecast archive?** It stitches together the freshest model runs, so the values were effectively forecast just before they happened. Backtesting on it would overstate real planning skill. **This is look-ahead bias, and avoiding it is a core design decision.** Log it in DECISIONS.md and explain it on the Methodology page.
- The Previous Runs API stores **total cloud cover only** (no low/mid/high layers). Layers are shown only in the live view.
- Features computed over the night's dark hours:
  - `frac_clear` — fraction of dark hours with forecast ≤ threshold
  - `longest_clear_run` — longest consecutive clear run, in hours
  - `longest_clear_run_frac` — `longest_clear_run / dark_hours`
  - `mean_cover` — mean cloud fraction
  - `pred_usable` — boolean, the usable-night rule applied to the forecast
- If more than 25% of dark hours are missing for a model/lead, that model's features for that night are NaN (handled in 8.4).

### 4.8 Seasons
- DJF (winter), MAM (spring), JJA (summer), SON (fall).

## 6. Data sources (verify every detail in Phase 0)

### 6.1 Open-Meteo Previous Runs API — historical forecasts at fixed lead times
- Base URL: `https://previous-runs-api.open-meteo.com/v1/forecast`
- Hourly variables: `cloud_cover_previous_day1` … `cloud_cover_previous_day7` (same naming pattern as the documented `temperature_2m_previous_day1`).
- Archive: most models from **January 2024**.
- Target models (look up the exact `models=` identifiers in Open-Meteo's docs and confirm by probing):
  - NCEP **GFS**
  - NCEP **HRRR** (CONUS)
  - NCEP **NAM** (CONUS)
  - **ECMWF IFS** (HRES 9 km if available in this API, otherwise 0.25°)
  - Optional, if cheap to add: GEM (Canada), DWD ICON
- Regional models have short horizons, so only some leads exist (e.g. HRRR likely only lead 1–2). **Build a table in DATA_NOTES of which leads are actually populated per model**, and handle missing leads everywhere.
- Figure out: date-range parameters (`start_date`/`end_date` vs `past_days`), the maximum range per request, and how multiple models come back in one response. Chunk requests (e.g. by month) if needed.

### 6.2 Open-Meteo Historical Weather API — ERA5 reanalysis (label source)
- Base URL: `https://archive-api.open-meteo.com/v1/archive` (confirm).
- Model: ERA5 (confirm the identifier).
- Hourly: `cloud_cover`, plus `cloud_cover_low`, `cloud_cover_mid`, `cloud_cover_high` if available.
- Measure the current publication lag and record it.

### 6.3 Open-Meteo Forecast API — live forecasts
- Base URL: `https://api.open-meteo.com/v1/forecast`
- Same models as 6.1, `forecast_days=8`, `timezone=UTC`.
- Hourly: `cloud_cover`, `cloud_cover_low`, `cloud_cover_mid`, `cloud_cover_high`. For display: `temperature_2m`, `dew_point_2m`, `wind_speed_10m`, `wind_gusts_10m`.

### 6.4 IEM ASOS/METAR archive — observations (label source)
- Endpoint: `https://mesonet.agron.iastate.edu/cgi-bin/request/asos.py`
- Parameters (documented):
  - `station` (repeatable)
  - `data=skyc1,skyc2,skyc3,skyc4,skyl1,skyl2,skyl3,skyl4,metar` (keep the raw `metar` for debugging)
  - `sts` / `ets` as ISO UTC timestamps
  - `tz=UTC`
  - `format=onlycomma`
  - `elev=yes`
- Limits: rate-limited per IP; returns HTTP 503 under heavy load; requests over ~1,000 station-years are rejected with HTTP 422. **Request one station × one year at a time.**
- Station metadata comes from IEM's network metadata for `CA_ASOS` (find the current endpoint; a GeoJSON network listing exists).

### 6.5 HTTP client, caching, and etiquette
- **All HTTP goes through one module** (`skytrust/data/http.py`) with:
  - a 30 s timeout
  - retries with exponential backoff and jitter on 429/5xx (max 5 attempts)
  - a small polite delay between calls
  - a descriptive User-Agent that includes the repo URL
  - typed exceptions (`SourceUnavailableError`, `BadResponseError`)
- **Disk cache:** raw responses go to `data/raw/{source}/{site}/{model_or_na}/{start}_{end}.{json|csv}`. Re-running any fetch command must make **zero network calls** if the cache is complete. Provide a `--refresh` flag to bypass it.
- Check Open-Meteo's current terms for free/non-commercial limits and stay well under them. Record the limits in DATA_NOTES.

### 6.6 Licensing and attribution
- Open-Meteo data is licensed **CC BY 4.0**. Attribute it in the app footer and the README.
- Credit the Iowa Environmental Mesonet for ASOS data.
- Do **not** scrape Clear Sky Chart or any light-pollution map imagery.

## 8. Modeling and evaluation (the core of the project)

### 8.1 Train/test split — fixed and time-based
- **Train:** nights 2024-01-01 → 2025-12-31
- **Test:** nights 2026-01-01 → latest labeled night
- Hyperparameter tuning happens **only inside train**, using `TimeSeriesSplit` (expanding window, 4 folds).
- **The test set is used once per final model.** Enforce this in code: a function asserts there's no date overlap, and a unit test checks that no test rows reach `fit()`.
- Why time-based: a random split would let the model train on future nights similar to test nights. That's leakage. Note this in LEARNING.md.

### 8.2 Baselines (all evaluated on test, per lead)
- **B1 Climatology:** P(usable) = training base rate for that (site, month).
- **B2 Persistence:** for lead d, predict the observed outcome of the night d nights earlier. That outcome is known at decision time, so there's no leakage.
- **B3 Single model, rule-based:** `m_pred_usable` as a hard yes/no. Report confusion-matrix metrics only (a hard 0/1 has a poor Brier score by construction).
- **B4 Single model, calibrated:** logistic regression on that one model's features, fit on train. This is the fair "best single model" comparison.
- **B5 Equal-weight average:** mean of available models' `frac_clear` used directly as a probability. This shows whether *learned* weights add anything.

### 8.3 Main model: the blend
- **One model per lead d** (d = 1…7; only the leads with enough data).
- scikit-learn `Pipeline`:
  - `SimpleImputer(strategy="median", add_indicator=True)` for missing model features
  - `StandardScaler`
  - `LogisticRegression` with L2 penalty; tune `C` via `TimeSeriesSplit` on log loss
- Features:
  - each available model's `frac_clear`, `longest_clear_run_frac`, `mean_cover`
  - `spread_frac_clear`
  - site one-hot
  - month encoded as `sin(2πm/12)` and `cos(2πm/12)`
  - `dark_hours`
- No class weighting (we want calibrated probabilities, not balanced accuracy).
- **Calibration check:** plot reliability on CV folds. Only if CV shows clear miscalibration, wrap the model in `CalibratedClassifierCV(method="isotonic", cv=TimeSeriesSplit(...))`. Record the decision and evidence in DECISIONS.md.
- **Interpretability:** output the coefficient table (which model the blend trusts most, and how that changes with lead) and explain it in RESULTS.
- **Optional, only after everything else is done:** compare against `HistGradientBoostingClassifier`. Keep logistic regression as the shipped model unless the gain is large and CV-confirmed.

### 8.4 Missing models
- Some leads won't have every model (e.g. HRRR at long leads). Handle this with the imputer + missing indicators, and train each lead's model only on the models present for that lead.

### 8.5 Metrics
Computed on the test set, per lead: overall, per site, per season, and per label type.
- **Brier score**, and **Brier Skill Score** vs climatology: `BSS = 1 − BS / BS_climatology`
- **Log loss**
- **ROC AUC**
- **Reliability diagram:** 10 equal-width bins, with counts per bin shown
- At a decision threshold (default 0.5, configurable):
  - **False-clear rate** = FP / (TP + FP): of the nights we said "go," the share that turned out not usable. This is the headline metric because it's the #1 user complaint.
  - **Miss rate** = FN / (TP + FN): of the truly usable nights, the share we told people to skip.
  - Accuracy and base rate
- **Uncertainty:** 95% CIs via **block bootstrap by calendar week** (1,000 resamples, fixed seed). Nights are autocorrelated, so a naive bootstrap overstates confidence.
- **Paired bootstrap** for (blend − best single model) and (blend − climatology) differences.

### 8.6 Lead-time skill curves
- BSS and false-clear rate vs lead (1…7) for each model, the equal-weight average, and the blend.
- The live 7-night outlook uses these curves to show how much each night's number can be trusted.

### 8.7 Model artifacts
- Export each lead's trained model to **JSON**, not pickle: `artifacts/model_lead{d}.json`. Include:
  - feature names in order
  - imputer medians + indicator columns
  - scaler means and scales
  - coefficients and intercept
  - calibration mapping if used
  - training period, library versions, created timestamp, git commit hash
- A pure-numpy loader rebuilds `predict_proba` from the JSON. **Unit test:** the JSON model reproduces sklearn's predictions to within 1e-9.
- `artifacts/metrics.json` holds every metric the app and README display.

### 8.8 Results document
- `docs/RESULTS.md`, generated by `skytrust report`, with tables and figures in `docs/figures/*.png`.
- Must include:
  - headline table
  - lead-time curves
  - reliability diagrams
  - per-site/per-season breakdowns
  - sensitivity across label types
  - coefficient table
  - an explicit **Caveats** section: ASOS 12,000 ft blind spot, ERA5 is reanalysis and ECMWF-related, point vs grid representativeness, 2026 test period is a single year, and the lead-1 vs live "tonight" mismatch
- **Honesty rule:** if the blend doesn't beat the best single model with a CI excluding zero, say so in one plain sentence. Don't hunt for thresholds or subsets that make it look better.

## 9. Live forecast — "present" and "future"

`skytrust/live.py`, used by both the CLI and the app.

1. For each site, fetch the live Forecast API (6.3) for all models.
2. Identify upcoming nights:
   - "Tonight" = the night whose dark window is current (if now is inside a dark window) or next.
   - Then the following 6 nights.
3. **Lead assignment:** `d = max(1, ceil((dusk_utc − now_utc) / 24h))`, capped at 7.
   - Tonight → 1, tomorrow night → 2, and so on.
   - Document the mismatch: the live "tonight" forecast is fresher than lead-1 training data, so its probability is slightly conservative. Say this on the Methodology page.
4. Compute the same features as training, then apply the lead-d JSON model → `P(usable)`.
5. Output per night:
   - `P(usable)` and a **verdict**: Go (≥ 0.70) / Maybe (0.40–0.70) / Skip (< 0.40), with thresholds configurable
   - **Best window:** the longest run of dark hours where the **median across models** is ≤ threshold (start, end, length)
   - **Model agreement:** "Models agree" / "Models split," based on `spread_frac_clear` (threshold configurable, set from the train distribution)
   - **Track record at this lead and site:** test-set false-clear rate and BSS pulled from `metrics.json`
   - Per-model hourly cloud cover (and low/mid/high layers where available)
   - Moon: illumination %, moonrise/moonset, moon-free dark hours; dusk/dawn times
6. **Resilience:**
   - Cache live responses (Streamlit `st.cache_data`, TTL 60 min, plus a last-good copy on disk).
   - If the API fails, show the last good forecast with a clear "as of <time>" banner.
   - If a single model is missing, compute with the models available and say so.
   - **Never crash the app.**
7. CLI: `python -m skytrust tonight --site SAC` prints the same information as text.

## 10. The app (Streamlit)

**The app only reads precomputed artifacts plus live forecasts. It never trains or backfills.** Plotly for charts. Dark theme; mobile-friendly layout.

**Page 1 — Tonight**
- Site picker (default: SAC)
- Big `P(usable)` number + verdict (Go / Maybe / Skip)
- Best window
- Model-agreement badge
- "How reliable is this?" card: false-clear rate and BSS at this site and lead from the backtest, with CIs
- Darkness + moon timeline bar (dusk → dawn, moon up/down)
- Hourly chart: each model's cloud cover + the median, with the clear threshold drawn as a line
- Low/mid/high layers where available

**Page 2 — 7-Night Outlook**
- One card/row per night: date, P(usable), verdict, best window, moon-free dark hours
- A trust indicator that drops with lead, driven by the lead-time curves (8.6)

**Page 3 — Track Record (the backtest)**
- False-clear rate per model vs the equal-weight average vs the blend (bars with 95% CIs)
- Reliability diagram
- BSS vs lead curves
- Per-site and per-season breakdowns
- A label-source toggle: primary / ASOS-only / ERA5-only
- Plain-English takeaways **generated from `metrics.json`** (template sentences filled with real numbers, never hand-typed)

**Page 4 — Methodology**
- Plain English: the problem, the definitions (Section 4), data sources, the look-ahead-bias decision, the time-based split, the caveats (8.8), and attribution

**Nice touch (small, optional):** a "night vision" toggle that switches to a red-on-black palette. Astronomers use red light to preserve dark adaptation.

**Performance:** first load under ~5 seconds on Streamlit Community Cloud, using cached artifacts.

### 12.1 Required unit tests (minimum; add more as you find edge cases)

**astro**
- Dusk/dawn for the SAC coordinates on 2025-06-21 and 2025-12-21 match an **independent** reference within ±2 minutes. Use a different library (e.g. `astral` with an 18° depression, as a test-only dependency) or a published table. Document which one.

- Moon illumination on a known full-moon date is > 0.98; on a known new-moon date it's < 0.02.

**METAR parsing (iem)**
- Every code in the 4.6(a) table maps correctly, in both default and conservative mode.
- Max over layers; VV → 1.0; missing → NaN.
- Window assignment: an obs at H+30 min is included; an obs at exactly H−30 min is excluded.
- Multiple obs in a window (routine + SPECI) → max.

**Usable-night rule**
- Exactly 3 consecutive clear hours → True; 2 → False.
- Clear hours separated by a missing hour are not consecutive.
- Cover exactly equal to the threshold (0.20) counts as clear.
- Empty dark window → excluded, not False.

**Features**
- A synthetic hourly series gives known `frac_clear`, `longest_clear_run`, `mean_cover`.
- The >25%-missing rule sets features to NaN.

**Labels**
- Per-hour max combination.
- The missing-coverage exclusion rule and its logged reason.

**Split and leakage**
- Train max date < test min date.
- A spy/fixture proves no test rows reach `fit()`.
- Climatology and imputer statistics are computed from train only.

**Metrics**
- Brier, BSS, and log loss match sklearn / hand-computed values on tiny arrays.
- Block bootstrap is reproducible with a seed.
- Reliability bin counts sum to n.

**Model export**
- The JSON model round-trip reproduces sklearn `predict_proba` within 1e-9.

**HTTP / clients**
- Parse the recorded fixtures for every source.
- 503 → retries, then raises `SourceUnavailableError`.
- Empty or malformed payload → `BadResponseError`.
- A complete cache → zero network calls (mock the session and assert it's never called).

**Live**
- Lead assignment for: afternoon before dusk, inside the dark window, after midnight but before dawn.
- API failure → last-good fallback with a timestamp.
- One model missing → still returns a result with `n_models_available` reduced.

**Dataset validation**
- Cloud fractions in [0, 1].
- `(site, night_date, lead)` is unique.
- `dark_hours` within a plausible range for California latitudes (about 4–13).
- No naive timestamps.

## 18. Glossary (for me — keep LEARNING.md consistent with these)

- **Lead time:** how far ahead a forecast was made. Lead 1 ≈ issued 24 h before the valid time.
- **Look-ahead bias:** accidentally using information that wouldn't have been available when the decision was made. It makes backtests look better than reality.
- **Brier score:** mean squared error of probability forecasts vs 0/1 outcomes. Lower is better; 0 is perfect.
- **Brier Skill Score (BSS):** improvement over a reference (climatology). 0 = no better than climatology; 1 = perfect; negative = worse.
- **Calibration / reliability:** when the model says 70%, does it happen ~70% of the time? A reliability diagram plots predicted vs observed frequency.
- **Log loss:** penalizes confident wrong predictions heavily.
- **Climatology:** the historical base rate (e.g. how often SAC nights in January were usable).
- **Reanalysis (ERA5):** a best estimate of past weather, made by running a model constrained by historical observations.
- **METAR / ASOS:** standardized airport weather reports from automated stations; sky cover is reported in oktas (eighths of the sky).
- **Block bootstrap:** resampling whole weeks instead of single nights, so the confidence intervals respect the fact that consecutive nights are correlated.
- **TimeSeriesSplit:** cross-validation that always trains on the past and validates on the future.
- **Logistic regression:** a model that outputs a probability from a weighted sum of features. Its coefficients show which inputs it relies on.
